# Research decisions for 0.3.0

Reviewed 2026-10-23. These are primary upstream sources, not an exhaustive ranking of every coding product. Direct documentation hosts were blocked by the cloud's network policy, so official GitHub source/documentation was used. No upstream application code was copied. This app does not embed the referenced products or claim feature parity.

## What the research changes in practice

1. **The runtime defines what happened.** A JSON-looking tool request in prose is not a tool call. It is never executed as a fallback.
2. **Recovery is bounded and observable.** The model can correct its response using native tools. If it cannot, the app reports `protocol_error`, preserving useful evidence without pretending the coding task completed.
3. **“Responded,” “executed,” “verified,” and “goal met” differ.** Conversation-only turns have `response_only`; failed/denied actions have `needs_review`; completion of actual tool execution remains distinct from a user assessment of the goal.
4. **A diagnostic suite must be safe and specific.** The installed app runs built-in checks on disposable files. It does not run arbitrary tests found in a user project or silently invoke paid cloud models.
5. **Collection should support a decision.** Record app/suite/schema versions, expected vs actual outcomes, durations, error classes, recovery outcomes and relevant model/server metadata. Do not accumulate every secret, file or token in a giant log.
6. **Sharing is a separate lifecycle.** A local report is not a GitHub issue until explicitly submitted and confirmed. A browser draft is not proof of upload. A timed-out POST is not automatically retried because it may already have created an issue.
7. **Source releases and support data should stay separate.** Use GitHub Issues for approved support reports, source control for implementation/regression tests, and GitHub Releases for verified installers. User diagnostic histories do not belong in permanent source Git history by default.

## Deliberately deferred

Full agent teams, uncontrolled self-modification, automatic benchmark-driven prompt mutation, whole-project content collection, complete checkpoint/rollback support, hosted observability, independent update signing and registered GitHub OAuth are not claimed implemented. The current improvement loop is: observe → diagnose → approve sharing → reproduce → test a change → publish a verified release.


## 0.4.0 metadata/protocol follow-up

Reviewed the first-party [Ollama API contract](https://github.com/ollama/ollama/blob/main/docs/api.md) and [OpenAI model resource](https://github.com/openai/openai-python/blob/main/src/openai/resources/models.py): model listing is separate from chat/generation. The app uses GET `/api/tags` for Ollama and GET `/models` for compatible services, with no generation request. Ollama `/api/show` template/capability metadata is collected only during the separate optional local workflow; the template is hashed, not saved. No raw user keys or live paid model calls were available in the cloud. Compatible provider support is contract-based and still requires the user's live metadata acceptance; no universal credential/tool certification is inferred from a list.

The practical retention decision is bounded structured records plus a stable maintenance index, not an expanding pile of raw logs. Same-suite/model comparisons distinguish measurement changes from behavioral changes. Existing Issues #1/#2 provide a baseline; additional structure is needed before identifying the live protocol cause.
